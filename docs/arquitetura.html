Fluxo de uma execução, guardrails e governança

Como o agente produz um relatório e quais controles atuam em cada etapa. Todos os eventos ficam na trilha de auditoria da execução.

Fluxo de uma execução

  1. Pedido: o usuário informa a UF (ou Brasil) e, opcionalmente, um foco. Os guardrails de entrada validam o pedido antes de qualquer chamada ao LLM.
  2. Orquestração: o LLM recebe as três tools e decide quais chamar (normalmente as três, em paralelo). Os argumentos são uma enumeração fechada de UFs: o LLM não escreve SQL nem consultas de busca.
  3. Execução das tools: métricas e séries vêm de SQL fixo no DuckDB somente leitura; notícias passam por triagem anti-injeção e mascaramento de PII. Tudo fica no RunContext.
  4. Cobertura: se o LLM não chamou alguma tool obrigatória ou estourou o limite de passos, o grafo a executa de forma determinística e registra o motivo.
  5. Redação: o LLM escreve a análise em formato estruturado (Pydantic), a partir das métricas, das séries e das notícias, que chegam marcadas como conteúdo não confiável.
  6. Validação: percentuais e contagens precisam bater com os dados; citações de notícias precisam existir; o texto não pode conter instruções nem dados pessoais. Se reprovar, o LLM recebe o motivo e reescreve (até 2 tentativas); persistindo, o relatório sai com aviso explícito.
  7. Relatório: tabela de métricas, gráficos e lista de fontes são montados a partir dos dados; o LLM contribui apenas com os textos interpretativos.

Camadas de guardrails

CamadaControle
EntradaUF em lista fechada; foco ≤ 300 caracteres, restrito ao tema, sem padrões de injeção nem dados pessoais.
DadosBanco aberto em modo somente leitura; consultas SQL fixas e parametrizadas; LLM sem acesso a SQL.
ToolsSchema estrito; tool desconhecida ou argumento inválido vira erro devolvido ao LLM; limite de passos do orquestrador.
Conteúdo externoNotícias com padrões de injeção são descartadas; PII mascarada; texto entregue ao LLM como não confiável.
SaídaPercentuais e contagens conferidos com os dados; ids de notícias verificados; detecção de instruções; mascaramento de PII; revisão automática.
ResiliênciaModelo reserva quando o principal está sobrecarregado (Gemini) ou recusa a requisição (Claude); falha das notícias não derruba o relatório.

Dados sensíveis

  • O ETL lê só 21 das 194 colunas (allowlist documentada no código).
  • Removidos antes de gravar: nº da notificação, data de nascimento, município, unidade de saúde, ocupação, lotes de vacina e todos os campos de texto livre.
  • Idade exata vira faixa etária; localização fica restrita à UF.
  • O LLM só recebe agregados (contagens e proporções), nunca registros individuais.
  • Dados brutos, banco, logs e .env ficam fora do Git.

Governança e transparência

  • Trilha de auditoria JSONL por execução, com sequência e horário de cada evento.
  • Cada métrica traz numerador, denominador, período, definição e limitações.
  • Prompts versionados no código; hash do prompt registrado a cada chamada.
  • O relatório informa modelo usado, data de corte, data de referência e id da execução.
